# M1.5 Draft — top-three implementation spec

Concrete schema + policy changes for the three highest-priority M1.5 items:
1. Registration lockdown
2. User deactivation (`IsActive`)
3. Finance + Delegate role split

Scope discipline (per CLAUDE.md): each change touches the minimum surface. Config
toggles mirror the existing `Database:Provider` / `Auth:EnableEntraId` pattern.
Every schema change is one EF migration. Nothing here recomputes or destroys
history — deactivation and role changes are reversible.

---

## 1. Registration lockdown

**Problem:** `Register.cshtml.cs` is `[AllowAnonymous]` and mints an Employee for
anyone who reaches the URL. Unacceptable for a system holding itineraries + (M3)
card/PII data.

**Approach:** one config switch selects the mode. Domain allowlist is the simplest
prod-safe default; invite-only for locked-down orgs; open only for demo/eval.

### 1a. Config

```jsonc
// appsettings.json
"Auth": {
  "Registration": {
    "Mode": "Domain",                       // Open | Domain | Invite | Closed
    "AllowedDomains": [ "yourco.com" ]       // used when Mode = Domain
  }
}
```

### 1b. Policy helper (new: `Domain/RegistrationPolicy.cs`)

```csharp
namespace TravelTracker.Web.Domain;

public enum RegistrationMode { Open, Domain, Invite, Closed }

public static class RegistrationPolicy
{
    public static RegistrationMode Mode(IConfiguration c) =>
        Enum.TryParse<RegistrationMode>(c["Auth:Registration:Mode"], true, out var m)
            ? m : RegistrationMode.Closed;   // fail closed on a bad/missing value

    // Self-serve register page is reachable only in Open/Domain.
    public static bool SelfServeAllowed(IConfiguration c) =>
        Mode(c) is RegistrationMode.Open or RegistrationMode.Domain;

    public static bool EmailAllowed(IConfiguration c, string email)
    {
        switch (Mode(c))
        {
            case RegistrationMode.Open:
                return true;
            case RegistrationMode.Domain:
                var domains = c.GetSection("Auth:Registration:AllowedDomains")
                               .Get<string[]>() ?? Array.Empty<string>();
                var at = email.LastIndexOf('@');
                if (at < 0) return false;
                var host = email[(at + 1)..].Trim().ToLowerInvariant();
                return domains.Any(d => string.Equals(d.Trim(), host,
                    StringComparison.OrdinalIgnoreCase));
            default:                          // Invite, Closed -> no self-serve
                return false;
        }
    }
}
```

### 1c. Register page changes

`Register.cshtml.cs` — gate both handlers:

```csharp
public IActionResult OnGet(string? returnUrl = null)
{
    if (!RegistrationPolicy.SelfServeAllowed(_config))
        return RedirectToPage("/Account/Login");   // hide the form entirely
    ReturnUrl = returnUrl;
    return Page();
}

public async Task<IActionResult> OnPostAsync(string? returnUrl = null)
{
    if (!RegistrationPolicy.SelfServeAllowed(_config))
        return Forbid();

    returnUrl ??= Url.Content("~/");
    if (!ModelState.IsValid) return Page();

    if (!RegistrationPolicy.EmailAllowed(_config, Input.Email))
    {
        ModelState.AddModelError("Input.Email",
            "Registration is restricted to approved company email addresses.");
        return Page();
    }
    // ...existing CreateAsync + AddToRole(Employee) + SignIn...
}
```

Inject `IConfiguration _config` via the constructor (Login already reads config
this way).

## 2. User deactivation (`IsActive`)

**Problem:** no way to offboard a leaver. Hard-delete is already blocked (FKs are
`Restrict`), so deactivation is the intended lifecycle. Must (a) block new
sign-ins and (b) kill existing sessions immediately.

### 2a. Schema — `AppUser.cs`

```csharp
// True = can sign in. Set false to offboard without deleting history.
public bool IsActive { get; set; } = true;
```

Migration:

```
dotnet ef migrations add AddUserIsActive -p src/TravelTracker.Web
```

Existing rows default to `true` (column default). Verify the generated migration
sets `defaultValue: true` so seeded/legacy users stay enabled.

### 2b. Enforce at sign-in — custom `SignInManager`

`CanSignInAsync` is the hook Identity calls inside `PasswordSignInAsync`, so this
covers local login, and the security-stamp check (below) covers live cookies and
Entra sessions.

`Data/AppSignInManager.cs` (new):

```csharp
using Microsoft.AspNetCore.Identity;
using TravelTracker.Web.Data.Entities;

namespace TravelTracker.Web.Data;

public class AppSignInManager : SignInManager<AppUser>
{
    public AppSignInManager(
        UserManager<AppUser> userManager,
        Microsoft.AspNetCore.Http.IHttpContextAccessor contextAccessor,
        IUserClaimsPrincipalFactory<AppUser> claimsFactory,
        Microsoft.Extensions.Options.IOptions<IdentityOptions> optionsAccessor,
        Microsoft.Extensions.Logging.ILogger<SignInManager<AppUser>> logger,
        Microsoft.AspNetCore.Authentication.IAuthenticationSchemeProvider schemes,
        IUserConfirmation<AppUser> confirmation)
        : base(userManager, contextAccessor, claimsFactory, optionsAccessor,
               logger, schemes, confirmation) { }

    public override async Task<bool> CanSignInAsync(AppUser user)
    {
        if (!user.IsActive) return false;      // deactivated -> no sign-in
        return await base.CanSignInAsync(user);
    }
}
```

Register it in `AuthSetup.AddAppIdentity`, and shorten the cookie-revalidation
interval so deactivation kicks live sessions promptly:

```csharp
services.AddIdentity<AppUser, IdentityRole>(options => { /* ...existing... */ })
    .AddEntityFrameworkStores<AppDbContext>()
    .AddDefaultTokenProviders()
    .AddSignInManager<AppSignInManager>();     // <-- add

services.Configure<SecurityStampValidatorOptions>(o =>
    o.ValidationInterval = TimeSpan.FromMinutes(1));
```

When deactivating, call `UpdateSecurityStampAsync` so the next revalidation (<=1
min) invalidates the user's existing cookie. `CanSignInAsync` then refuses the
re-issue.

### 2c. Admin UI — `Admin/Users/Index`

Add row status + toggle handlers. Include the **last-admin guard** here (M1.5
must-have) so you can't disable the final Admin.

```csharp
public async Task<IActionResult> OnPostToggleActiveAsync(string id)
{
    var user = await _userManager.FindByIdAsync(id);
    if (user is null) return NotFound();

    if (user.IsActive && await IsLastActiveAdminAsync(user))
    {
        TempData["Error"] = "You cannot deactivate the last active administrator.";
        return RedirectToPage();
    }

    user.IsActive = !user.IsActive;
    await _userManager.UpdateAsync(user);
    await _userManager.UpdateSecurityStampAsync(user);   // revoke live sessions
    return RedirectToPage();
}

private async Task<bool> IsLastActiveAdminAsync(AppUser candidate)
{
    var admins = await _userManager.GetUsersInRoleAsync(Roles.Admin);
    return admins.Count(a => a.IsActive) <= 1
        && admins.Any(a => a.Id == candidate.Id);
}
```

Extend the `Row` record with `bool IsActive` and render a Deactivate/Reactivate
button + a muted "Inactive" badge. Deactivated users stay listed (history intact).

> The same `IsLastActiveAdminAsync` guard belongs in `Users/Edit` before a role
> change that would demote the last Admin.

## 3. Finance + Delegate (Arranger) role split

> **Shipped.** Both roles added; Arranger scoping threaded through every trip surface;
> full `Admin/Arrangers` assignment UI built. Access decisions stay pure in
> `TripAccess` (`CanAccess` + `Scope`/`TripScope`); the only DB piece is the thin
> `ArrangerAccess` lookup. Migration `AddArrangerAssignments`. See `tasks/todo.md`.

**Problem:** three flat roles conflate "reimburses money" (Finance) with "runs the
system" (Admin), and today any Manager/Admin can act for *everyone*. Real orgs
scope an arranger to specific travelers.

### 3a. New roles — `Roles.cs`

```csharp
public const string Employee = "Employee";
public const string Arranger = "Arranger";   // travel arranger / delegate (scoped)
public const string Manager  = "Manager";
public const string Finance  = "Finance";    // sees expenses/reports, not accounts
public const string Admin    = "Admin";

public static readonly string[] All =
    { Employee, Arranger, Manager, Finance, Admin };
```

`DbInitializer.SeedAsync` already loops `Roles.All`, so the two new roles seed
automatically on next startup. No migration needed for the role rows themselves.

### 3b. Policies — `AuthSetup.AddAppIdentity`

```csharp
services.AddAuthorization(options =>
{
    options.AddPolicy("RequireAdmin",   p => p.RequireRole(Roles.Admin));
    options.AddPolicy("RequireManager", p => p.RequireRole(Roles.Manager, Roles.Admin));
    // Finance can see all expenses/reports (M3/M4) without account god-mode.
    options.AddPolicy("RequireFinance", p => p.RequireRole(Roles.Finance, Roles.Admin));
});
```

Finance is additive and low-risk now; it earns its keep when M3 expense views and
M4 reporting folders get `AuthorizeFolder(..., "RequireFinance")`.

### 3c. Delegate scoping — the one that changes access logic

An Arranger manages only assigned travelers. Introduce a mapping table and stop
treating "can manage others" as global.

New entity `Data/Entities/ArrangerAssignment.cs`:

```csharp
public class ArrangerAssignment
{
    public int Id { get; set; }
    public string ArrangerId { get; set; } = "";   // AppUser (Arranger role)
    public AppUser? Arranger { get; set; }
    public string TravelerId { get; set; } = "";    // AppUser they may act for
    public AppUser? Traveler { get; set; }
}
```

`AppDbContext`: `DbSet<ArrangerAssignment> ArrangerAssignments`, unique index on
`(ArrangerId, TravelerId)`, FKs `Restrict` (match existing AppUser FK policy so no
cascade-delete of people). Migration `AddArrangerAssignments`.

Update `Domain/TripAccess.cs` — keep it pure (no DB in the domain layer) by passing
in the caller's delegated traveler ids:

```csharp
// Admin/Manager keep global reach; an Arranger reaches only assigned travelers.
public static bool CanManageOthers(ClaimsPrincipal user) =>
    user.IsInRole(Roles.Manager) || user.IsInRole(Roles.Admin);

public static bool CanAccess(
    ClaimsPrincipal user, Trip trip, IReadOnlySet<string>? delegatedTravelerIds = null)
{
    var uid = user.FindFirstValue(ClaimTypes.NameIdentifier);
    if (trip.TravelerId == uid) return true;
    if (CanManageOthers(user)) return true;
    return user.IsInRole(Roles.Arranger)
        && delegatedTravelerIds is not null
        && delegatedTravelerIds.Contains(trip.TravelerId);
}
```

Thin service to load the set (page models call this, domain stays pure):

```csharp
// Domain/ArrangerAccess.cs
public class ArrangerAccess(AppDbContext db)
{
    public async Task<HashSet<string>> DelegatedTravelerIdsAsync(string arrangerId) =>
        (await db.ArrangerAssignments
            .Where(a => a.ArrangerId == arrangerId)
            .Select(a => a.TravelerId)
            .ToListAsync()).ToHashSet();
}
```

Traveler pickers on Create (Manager/Admin see all users; an Arranger sees only
assigned travelers) read from the same set. Admin UI `Admin/Arrangers` to assign
traveler <-> arranger (deferred sub-task; the table + access check are the core).

## 4. Self-service password (reset + change) + email

**Problem:** a locked-out user had no recovery path (admin reset only), and a
signed-in user couldn't rotate their own password. Identity's token providers are
already wired (`AddDefaultTokenProviders`); the missing pieces were the pages and a
way to actually deliver mail. Registration/invite flow is **unchanged** — the
Register page still doubles as invite acceptance.

### 4a. Email port — `Services/IEmailSender.cs`

One tiny port, provider-switched like `Database:Provider` / `Storage:Provider`:

```jsonc
"Email": {
  "Provider": "Log",                     // Log (default) | Smtp
  "FromAddress": "no-reply@example.com",
  "Smtp": { "Host": "", "Port": 587, "UseSsl": true, "Username": "", "Password": "" }
}
```

- `LoggingEmailSender` (default) writes the whole message to the log, so a dev copies
  the reset link out of the console — **no SMTP needed to work locally**. Never use
  in prod (one-time links land in the app log).
- `SmtpEmailSender` uses `System.Net.Mail.SmtpClient` (in the BCL, no extra package),
  reading `Email:*`. Selected with `Email:Provider=Smtp`.
- `Services/EmailSetup.AddAppEmail` does the switch; wired in `Program.cs`.

### 4b. Reset — anonymous, no account enumeration

- `Pages/Account/ForgotPassword` — generates a reset token only when the account
  exists **and** `IsActive` (a deactivated leaver gets nothing), base64url-encodes it,
  and emails a `ResetPassword` link. Always renders the same neutral confirmation, so
  the form can't be used to probe which emails are registered.
- `Pages/Account/ResetPassword` — email + token from the link → new password →
  `ResetPasswordAsync` → redirect to Login with a `resetSuccess` banner. Missing link
  params redirect back to ForgotPassword; a malformed/tampered token fails closed.
- `Login` gains a "Forgot your password?" link.

### 4c. Change — signed-in

- `Pages/Account/Manage/ChangePassword` — current + new → `ChangePasswordAsync`, then
  `RefreshSignInAsync` so the rotated security stamp doesn't bounce the session.
- `/Account/Manage` is folder-authorized in `Program.cs` (any signed-in user);
  `_LoginPartial` gains a "Change password" nav link.

### 4d. Admin reset — Admin/Users/Index

For the common help-desk case (user locked out, no email configured), an Admin resets
any account directly — no token round-trip.

- `Domain/TempPassword.Generate()` — the strong one-time-password generator, extracted
  from `Admin/Users/Create` so create and reset share it (satisfies the Identity
  policy: >=8 chars, lower + digit, padded to 16, crypto-shuffled).
- `IndexModel.OnPostResetPasswordAsync(id)` — mints a temp password and applies it via
  `GeneratePasswordResetTokenAsync` + `ResetPasswordAsync` (which rotates the security
  stamp, so the target's live sessions die at the next revalidation). The password is
  shown to the admin **once** via the same `NewUserPassword` alert as user creation
  (headline switched by `PasswordHeadline`); never stored in plaintext.
- `Admin/Users/Index` gains a per-row "Reset password" button (JS confirm). Admin-only
  because `/Admin` is folder-authorized `RequireAdmin`.

### 4e. Verification

Unit: `AddAppEmail` selects Log/Smtp by config (unknown → Log); `LoggingEmailSender`
completes with no SMTP. Integration (drives the real page handlers): forgot→reset
round-trip lets the user authenticate with the new password (old rejected); forgot
sends nothing for an unknown or deactivated address; a tampered token is refused;
change-password rotates on the right current password and is rejected on the wrong
one. Admin reset sets a fresh temp password (old rejected, new works, stamp rotated)
and returns NotFound for an unknown id; `TempPassword.Generate` always meets the
policy. Runtime smoke: ForgotPassword 200, ResetPassword-without-params → 302
ForgotPassword, ChangePassword unauth → 302 Login, POST forgot for the seeded admin
logs a full reset link, unknown email logs nothing; admin login → create user →
"Reset password" → the shown temp password logs the user in (old rejected).

No schema change — no migration. `IEmailSender` is reused by M5 notifications.

## 5. Entra group -> role JIT mapping (roles stop being hand-managed)

**Problem:** Entra login auto-provisions an Employee and then roles are assigned by
hand in `Admin/Users/Edit`. Enterprise expectation: the directory is the source of
truth for role membership.

### 5a. Config (`Auth:EntraId`)
```
"SyncRolesOnLogin": true,          // off switch; default true
"GroupClaimType": "groups",        // override to "roles" for app-role claims
"GroupRoleMappings": [             // many-to-many; empty = no-op
  { "GroupId": "<entra-group-object-id>", "Role": "Manager" },
  { "GroupId": "<entra-group-object-id>", "Role": "Finance" }
]
```
Emitting the `groups` claim is an app-registration setting (Token configuration ->
groups claim, or manifest `groupMembershipClaims`). Nothing is requested app-side.

### 5b. Pure mapper (`Domain/EntraRoleMapper.cs`)
- `ParseMappings` -> validated `EntraGroupRoleMap[]`; drops unknown roles / blank groups.
- `DesiredRoles(groupIds, maps)` -> roles the user should hold (group match is
  case-insensitive).
- `ManagedRoles(maps)` -> the set a sync is allowed to revoke.
- `Reconcile(current, desired, managed)` -> `(ToAdd, ToRemove)`. ToRemove is limited
  to managed roles no longer desired, so unmanaged (hand-granted) roles survive.

### 5c. Synchronizer (`Services/EntraRoleSynchronizer.cs`)
Reads config, extracts group ids from the principal, applies the plan via
`UserManager`. Guards: never strip Admin from the last active admin (`AdminGuard`);
bump the security stamp on change; detect the token-overflow overage claim and log
+ skip. `Enabled` gate = `EnableEntraId && SyncRolesOnLogin`; empty mappings = no-op.

### 5d. Wiring (`Pages/Account/ExternalLogin.cshtml.cs`)
- Returning linked user: `SyncAsync` then `RefreshSignInAsync` (immediate effect).
- Fresh provision: `SyncAsync` before `SignInAsync` (lands with roles, not just Employee).
- Registered `AddScoped<EntraRoleSynchronizer>()` in Program.

### 5e. Verification
- Unit: `EntraRoleMapperTests` (parse validation; desired from groups incl. case /
  multi-group; reconcile add/revoke; unmanaged preserved; empty no-op).
- Gate: `dotnet build -c Release` 0/0, `dotnet test` 190/190 green.
- `ExternalLogin` remains `[ExcludeFromCodeCoverage]` (live-IdP round-trip).

### 5g. App-role pass-through (recommended, near-zero config)
Instead of mapping group GUIDs, name the Entra **app roles** to match ours and honor
the `roles` claim value directly.

Config (one switch):
```
"RoleClaimPassthrough": true
```

Entra setup:
- App registration -> **App roles** -> add one role per app role; set **value** =
  `Employee` / `Arranger` / `Manager` / `Finance` / `Admin`; allowed member types = Users/Groups.
- Enterprise application -> **Users and groups** -> assign users (or whole groups) to those roles.
- No Token-configuration groups claim needed in this mode.

Behaviour (`EntraRoleMapper.PassthroughPlan`):
- desired = `roles` claim values matching `Roles.All` (canonical) + **Employee floor**.
- managed = every role except Employee -> Manager/Finance/Admin/Arranger fully mirror
  the directory (assign -> granted next login; unassign -> revoked). Employee is never revoked.
- Unknown claim values ignored; last-active-admin guard still applies.

Why prefer it: app roles are app-scoped and few, so no token-overflow/overage path;
config is readable role names, not GUIDs. Group mode (`GroupRoleMappings`) stays available
for GUID->role mapping when app roles are not an option.
